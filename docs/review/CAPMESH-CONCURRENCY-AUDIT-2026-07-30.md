**Summary:** capmesh persists to a single SQLite database (~/.capmesh/asg-capmesh.db, override CAPMESH_DB; state dir CAPMESH_STATE_DIR default ~/.capmesh). ### concurrency

**Summary:** The capmesh client-side relay (capmesh-http-relay.py) is a SINGLE shared Python process, spawned once by the gateway's BackendManager singleton and reused across ALL MCP sessions and all LLM clients (NOT one process per session). ### AUTH/IDENTITY resolution concurrency

**Summary:** Per-request identity resolution is NOT cheap in the recommended production mode. For direct tailnet peers (--interface tailscale0), `principal()` shells out to `tailscale whois` via a synchronous `subprocess.run(..., timeout=5)` with NO cache (no TTL, no per-IP memoization, no eviction), and `principal()` is not memoized on the request handler so it runs 2-3x per request — under 100s of concurrent requests this spawns 100s of `tailscale whois` subprocesses (pipe fds + LocalAPI socket contention) that block each handler thread up to 5s, exhausting fds and degrading auth (whois-fail → tailnet-guest → 401). Worse, the entire auth+handling path is serialized through a single global `threading.RLock` (`state_lock`): `ensure_identity_for_principal` takes it inside `principal()`, and `handle_jsonrpc`/`router.call` hold it for the whole request, so despite WAL + 60s busy_timeout + per-thread `ThreadLocalConnection` + mmap being correctly configured at the SQLite layer, the Python-level lock makes throughput effectively single-threaded. The proxy-token rename to CAPMESH_TRUSTED_PROXY_TOKEN is consistent across the install nginx header and server.py; the relay is unaffected (it uses the service bearer, not the proxy token), so no deployed-path mismatch. Google/JWKS network calls are login-callback-only, not per-request.

### Notes & caveats
- **Concurrency-ratio test deliberately NOT a speedup assertion.** On CPython a `ThreadingHTTPServer` is GIL-bound (Python-level scoring) and a single-process `ThreadPoolExecutor`+`urllib` client contends on the client GIL, so an absolute wall-clock speedup ratio is not a stable signal (a probe showed a 9.9× *slowdown* that was client-GIL contention, not server serialization). The tests therefore guard the load-bearing, robust properties: no deadlock/hang and correctness under concurrency, plus WAL write-safety (no BUSY / no lost updates). The `state_lock` removal is structurally verified by code review + the no-hang guard; a tight serialization-ratio regression test is not feasible on CPython single-process.
- **Pre-existing failures (NOT caused by these changes):** `tests/test_install_served_bytes_contract.py` (untracked operator WIP) — 4 failures: served `/install.sh` (from `_install_sh`, uses `CAPMESH_BASE`) drifted from on-disk canonical `install/install.sh` (uses `CAPMESH_BASE_URL`).
